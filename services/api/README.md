# api

The web API (task D1). It talks to alarm-core only through MQTT, using the topics and events documented in [alarm-core's README](../alarm-core/README.md), with its own broker account (`api`).

```
alarm_api/
  bridge.py    MQTT side: latest state, recent events, awaitable control requests
  app.py       FastAPI routes
  __main__.py  python -m alarm_api
```

> **No login yet (task D2).** Until then the server listens on **127.0.0.1 only**, and arm/disarm still require a valid alarm code. Don't expose it on a network before D2 and D5 are done.

## Endpoints

| Method | Path | Returns |
|---|---|---|
| GET | `/api/health` | MQTT connection, and how old the last state is |
| GET | `/api/state` | The latest `alarm/state` snapshot (503 until alarm-core has published one) |
| GET | `/api/events?limit=50&type=state&type=security` | Recent events, newest first (last 500 kept in memory) |
| POST | `/api/arm` `{"code": "1234"}` | Outcome (below) |
| POST | `/api/disarm` `{"code": "1234"}` | Outcome (below) |
| GET | `/docs` | Interactive documentation, generated by FastAPI |
| GET | `/metrics` | Prometheus metrics (list in [infra/monitoring/README.md](../../infra/monitoring/README.md)); duress never appears |
| GET | `/api/info` | Settings for the dashboard: `grafana_url` (from the `GRAFANA_URL` env var) |

Arm/disarm outcomes:

| `result` | HTTP | Meaning |
|---|---|---|
| `ok` | 200 | State changed; includes `state`, `prev` and `delay` when there is one |
| `no_change` | 200 | Accepted, nothing to do (e.g. disarm while already disarmed) |
| `bad_code` | 403 | Wrong code |
| `lockout` | 403 | This attempt started the 5-minute lockout |
| `locked` | 403 | Locked out, even the right code is refused |
| `arm_refused` | 409 | `detail` lists why (node offline, lid open, already armed) |
| (error) | 422 | The code isn't 4 to 8 digits |
| (error) | 504 | No reply from alarm-core within 3 s |

## How a request works

1. The API publishes `{"action": "arm", "code": ..., "source": "api", "req": <random id>}` on `alarm/control`.
2. alarm-core tags every event it emits for that request with the same `req`, and always ends with `control_done`.
3. The bridge collects the tagged events until `control_done` arrives, and the route turns them into the outcome above.

**Duress:** `duress` events are dropped as soon as they arrive. They're never stored, listed or returned. A duress disarm returns exactly what a normal disarm returns; `test_duress_disarm_is_indistinguishable` checks this. Only the notifier sends the silent alert.

## Event database (PostgreSQL)

When `DATABASE_URL` is set (the Docker stack sets it), every event is also stored in the `alarm_events` table, for history and search. Without it, events stay in memory only.

- **Never blocks:** the MQTT handler only queues the event (`database.EventStore.put`). One background thread keeps a connection open and writes in batches, so a slow database can't delay arm/disarm replies.
- **Never loses events:** if PostgreSQL isn't ready or goes away, events wait in the queue (up to 10,000; beyond that the oldest are dropped and counted) and are written when it comes back. In Docker, the API also waits for the database's healthcheck before starting.
- **Backfill:** events from before the API started never reach it over MQTT. On its first connection the store copies them from alarm-core's log (`data/events.jsonl`): everything with a `seq` above the highest one stored. `seq` is unique, so live events and the backfill never duplicate.
- **Same rules as the API:** `duress` events and replies (`status`, `control_done`) are never stored.
- **The log stays the source of truth.** The database isn't tamper-evident; `alarm_core verify-log` is.

`GET /api/health` shows the database side: `connected`, `pending`, `written`, `dropped`.

```bash
docker compose -f infra/docker/compose.yml exec postgres psql -U alarm -d alarm \
  -c "select seq, event_type, event_time from alarm_events order by seq desc limit 10"
```

## Running it

```bash
.venv/bin/pip install -e 'services/api[dev]'
scripts/dev-secrets.sh && docker compose -f infra/docker/compose.yml restart mosquitto   # once: adds the api account

.venv/bin/python -m alarm_core run          # terminal 1
.venv/bin/python -m alarm_sim node          # terminal 2
.venv/bin/python -m alarm_api               # terminal 3, then open http://127.0.0.1:8000/docs
```

```bash
curl localhost:8000/api/state
curl -X POST localhost:8000/api/arm -H 'content-type: application/json' -d '{"code":"1234"}'
```

## Tests

```bash
.venv/bin/pytest services/api
```

The tests run the real alarm-core and a simulated node behind the API, on an in-memory bus.
